02The one decision I need before Phase 1

Everything else in this plan can proceed on my judgment. This one changes the shape of the build, so it's yours to make.

⬥ Needs your call

Your spec requires that therapists never see each other's pay rates, tips, profit, or performance notes. The way every other login in this app works today (shared password, hidden in the UI) cannot actually guarantee that — anyone who opens their browser's developer tools can query the database directly with the same key the app uses. It would look restricted, but wouldn't be restricted.

The correct fix is to give each therapist a real account (Supabase Auth) and add database-level rules (Row Level Security) so the restriction is enforced by the database itself, not just by what buttons are on screen. This is new infrastructure for this app — more setup than the shared-password pattern used elsewhere — but it's the only way to honestly meet that requirement once real pay and tip data is involved.

If that's more than you need right now, the alternative is to launch with UI-only hiding (matching today's pattern everywhere else) and treat the payroll/pay-rate privacy as "trusted staff only, not adversarial" — faster, but not a real guarantee. I'd recommend real accounts given this handles people's pay.

06Concurrency & payment integrity

Two therapists claim the same request

When a booking has no assigned therapist yet (AWAITING_PRACTITIONER), eligible therapists see it in their queue. Claiming it is a single conditional database update — "assign me, but only if it's still unassigned" — so if two people tap Accept at the same instant, the database itself guarantees exactly one wins; the other sees it disappear from their queue immediately. No separate locking mechanism needed — Postgres does this natively and correctly.

Payment can never lie

The browser reporting "payment succeeded" is never trusted on its own — Stripe's server-to-server webhook is the only thing allowed to mark an appointment paid. This is what stops a closed tab, a flaky connection, or a tampered request from ever producing a confirmed-but-unpaid booking.

Folio posting can't double-charge

Each appointment gets one fixed reference (AMANSALA-SPA-{appointmentId}) used for every attempt. If Cloudbeds posting fails, the appointment is flagged FOLIO_POST_FAILED visibly (never silently marked successful), and admin's "Retry" reuses that same reference — so retries can't create a second charge.
